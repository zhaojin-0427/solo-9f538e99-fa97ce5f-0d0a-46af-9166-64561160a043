# 广播剧混音审听台

声音导演交片前的逐段审听工具：上传同一集的两条轨，按采样编号设置/清除静音，
两轨相加限幅到 16 位后按 5 秒一段逐段试听、确认，全部通过后方可下载整集 WAV。

## 快速开始

### Docker Compose（推荐）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

### 本地运行

```bash
pip install -r app/requirements.txt
python3 app/app.py          # 监听 0.0.0.0:8000，可用 PORT 环境变量修改
```

打开页面后点 **载入内置样例** 即可立即试听（27 秒、44.1 kHz、6 段；
第 3 段 10–11 秒处两轨同相叠加，可听到限幅效果）。样例也可直接播放：
`samples/sample_a.wav`、`samples/sample_b.wav`（由 `samples/make_samples.py` 生成）。

## 使用流程

1. **上传**同一集的两条轨（轨 A / 轨 B）：必须是 16 位单声道 PCM WAV，
   等长、同采样率，否则整体拒绝。
2. **静音编辑**：按采样编号为每轨维护若干半开区间 `[起, 止)`，可添加/删除/
   清除，点 **保存静音改动** 一次性原子保存。前端只提交本端改过的轨，
   未提交的轨保留服务端当前值；两个窗口分别编辑 A / B 轨并发保存不会互相覆盖。
   若同一轨在本窗口编辑期间已被他处保存，整次保存被拒绝并标出冲突轨，
   面板输入保留，可"载入服务端版本"后处理重提。
3. **逐段审听**：混音每 5 秒一段（末段可不足 5 秒）。每段先 **▶ 试听**
   再 **✔ 确认通过**；确认时服务端校验"刚试听的混音"与该段当前内容一致
   （SHA-256 哈希），不一致则拒绝并要求重新试听。
4. **下载整集**：全部段落通过后才可下载整集 WAV。

## 关键设计

- **通过状态由内容哈希驱动**：每段保存"曾被确认通过的混音哈希集合"，
  当前混音哈希 ∈ 集合即视为已通过。因此：
  - 保存静音后，**只有混音样本值实际变化的段**需要重听（哈希未变的段自动保持通过）；
  - 静音改回旧内容（如取消静音）时，若该内容此前已确认过，**自动恢复通过**，无需重听；
  - 集合中每个哈希都来自一次真实试听确认，不会放过未听过的内容。
- **保存原子性**：静音区间先全部校验、先在锁外算好全部新哈希，再一次性换入；
  任一区间非法 → 整体 400，**原混音与通过状态不变**。
- **按轨乐观并发（双窗口不互相抹静音）**：每轨静音表有独立版本号
  （`track_versions`）。保存请求只替换其中出现的轨，未出现的轨保持服务端现值，
  因此只提交一轨的旧调用、以及两个窗口分别改 A / B 轨的并发提交都能合并生效。
  请求可带 `base_versions` 声明各提交轨所依据的版本：版本不匹配说明同轨在编辑
  期间已被他处保存，整次拒绝（409、`conflicts` 标出冲突轨、回带服务端当前静音与
  客户端提交输入），不做静默覆盖；前端据此标红冲突轨并保留输入。哈希在锁外重算，
  重算期间另一轨被并发保存时自动取最新值重算重试（递增退避），极端繁忙时返回
  不带 `conflicts` 的 `retryable` 409，由客户端原样重试。
- **下载快照**：开始下载时（须全部通过）即快照轨道引用与静音表，之后流式生成。
  下载进行中他处改音/重传，**本次下载继续交付当时通过的混音**。
- **单段缓冲**：下载按段生成、逐段发送，应用层内存中最多暂存一段待发送的
  混音 PCM（源轨 PCM 整体常驻内存，这是混音的数据来源，非"待发送缓冲"）。
- **停读不阻塞**：流式生成器不持有全局锁；多线程 WSGI（waitress / Flask
  threaded）下，浏览器停读或断连只占用该下载自身线程，其他窗口的保存、
  试听、确认不受影响。
- **跨窗口共享**：状态保存在服务端单例中，所有窗口看到同一份审听进度；
  前端每 2 秒轮询同步他处改动（他处保存静音后本端段落状态自动刷新；
  未编辑的轨自动同步，正在编辑的轨保留输入并以横幅提示过期/冲突）。

## API 一览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 审听页面 |
| POST | `/api/upload` | 上传 `track_a` / `track_b` 两个 WAV（multipart） |
| POST | `/api/load_sample` | 载入内置样例 |
| GET | `/api/state` | 剧集信息、各段状态、静音表、总版本号与每轨版本号 |
| POST | `/api/mutes` | 保存静音 `{"A": [[s,e],...], "B": [...], "base_versions": {"A": n}}`（只出现的轨被替换，缺省轨保持原样）；返回失效段列表。同轨基线过期 → 409 + `conflicts`（回带服务端静音与客户端输入）；瞬时繁忙 → 409 + `retryable` |
| GET | `/api/segment/<i>.wav` | 第 i 段混音 WAV，响应头 `X-Mix-Hash` 为该段混音哈希 |
| POST | `/api/confirm/<i>` | 确认通过，请求体 `{"hash": 试听时拿到的哈希}` |
| GET | `/api/download` | 全部通过后才可下载整集 WAV（流式） |

## 交付报告

### 已做成

- 上传校验（16 位单声道 PCM、等长、同采样率、非空），失败整体拒绝
- 按采样编号的多段静音设置/清除，两轨原子保存；相加限幅到 16 位
- 5 秒分段（末段可不足），逐段试听（每段独立 WAV）+ 哈希一致性确认
- 哈希驱动的精确失效：仅实际变化的段需重听；内容复原自动恢复通过
- 保存失败保留原混音与通过状态（先校验后换入，锁外计算）
- **按轨乐观并发**：每轨独立版本号；保存只替换提交的轨，未提交轨保留服务端现值，
  两窗口分别改 A/B 并发提交自动合并；同轨编辑期被他处保存则整次 409 拒绝、
  标出冲突轨并回带服务端数据与客户端输入，前端标红、保留输入、可一键载入服务端版本
- **锁外重算可并发**：重算期间试听/确认不被阻塞；另一轨并发改动触发带退避的合并重试；
  瞬时繁忙返回 `retryable` 409，前端自动原样重试（同轨冲突不自动重试，须人工解决）
- 全通过才可下载；下载快照当时通过的混音；逐段流式生成（单段缓冲）
- 浏览器停读/断连不影响他人保存；内置可直接试听的样例；Docker Compose 启动

### 未完成 / 已知限制

- 单剧集单例：同时只能审一集，上传新集会覆盖旧状态（无多剧集/多用户隔离）
- 状态在内存中：服务重启后上传内容与通过记录丢失（无持久化）
- 未做身份认证与 HTTPS，假定内网/本机使用
- 源轨 PCM 整体驻留内存（512 MB 上传上限），超长剧集需自行调低上限或分集
- Docker 镜像未在本环境实际构建（环境无 docker/容器运行时且无 root）；
  Dockerfile/Compose 经静态核对，其入口 `waitress-serve app:app` 已用同一命令、
  同一 waitress 服务器在本地实测通过
- 前端为无框架单页，轮询同步（2 秒），未用 WebSocket；大段数列表未做虚拟滚动
- 极端高并发下合并重试可能达到上限而返回 `retryable` 409（前端已自动重试 5 次；
  4 线程 120 次混合压测下未再出现），同轨内容冲突则始终交由人工决定，不自动合并
